UMK Next Stage Plan

Based on the current state of the kernel and the vision we have reached, I do not advise adding mathematics to kernel/rust at this time. The next stage must prove that the kernel is generic enough, then we build the first mathematical system outside it.

Phase 0 — Freeze the Current Kernel

We do not add now:

· Polynomial
· Integer
· Matrix
· Group
· Calculus
· Specialized theorem prover
· Special algebraic rules

Inside the Kernel.

The goal is to stabilize the current architectural contract:

\boxed{
Expr \rightarrow Pattern \rightarrow Law
\rightarrow Rewrite \rightarrow Proof \rightarrow Verify
}

---

Phase 1 — Define the Boundary Between Kernel and Math Library

We organize the project approximately like this:

```
UMK/
│
├── kernel/
│   └── rust/
│       ├── expr
│       ├── pattern
│       ├── types
│       ├── rewrite
│       ├── proof
│       └── verify
│
├── math/
│   └── algebra/
│       ├── objects
│       ├── laws
│       ├── definitions
│       └── theorems
│
├── examples/
│
└── tests/
```

The core idea:

· kernel = mechanism
· math = knowledge

---

Phase 2 — Build the First "Math Package"

We do not start with all of mathematics.
We begin with the smallest serious system:

\boxed{\text{Elementary Algebra}}

We define externally:

Objects:

a,b,c,x,y,z

Operations:

+,\quad -,\quad \times

Constants:

0,\quad1

But all of these are definitions outside the kernel.

---

Phase 3 — Build Laws

For example:

a+0=a

a+(-a)=0

a+b=b+a

(a+b)+c=a+(b+c)

a\times1=a

a\times(b+c)=ab+ac

Each law becomes an object the kernel understands.
Conceptually, for example:

```
Law {
    lhs
    rhs
    variables
    conditions
}
```

The kernel does not know that this is the "associative law".
It only knows:

LHS \rightarrow RHS

---

Phase 4 — Test the Rewrite Engine with Real Mathematics

We take:

(a+b)^2

Then we make the system reach:

a^2+2ab+b^2

through a chain of laws.

For example:

(a+b)^2

\rightarrow (a+b)(a+b)

\rightarrow a(a+b)+b(a+b)

\rightarrow a^2+ab+ba+b^2

\rightarrow a^2+2ab+b^2

And most importantly:

We do not consider the result correct because the program said so.
Rather, we must have:

E_0
\xrightarrow{L_1}
E_1
\xrightarrow{L_2}
E_2
\xrightarrow{L_3}
\cdots
\xrightarrow{L_n}
E_n

Then:

\boxed{\operatorname{Verify}(Proof)=True}

---

Phase 5 — Separate "Definition" from "Law"

This is a very important step.
We need to distinguish between:

Definition
e.g.:

a^2 := a\times a

Law
e.g.:

a(b+c)=ab+ac

Theorem
e.g.:

(a+b)^2=a^2+2ab+b^2

Thus we have three layers:

```
Definition
     ↓
Law
     ↓
Theorem
```

The kernel can handle them with the same basic mechanism without knowing their mathematical meaning.

---

Phase 6 — Improve the Proof Object

Here I see a very important development.
Instead of the proof being just:

```
before
after
law
```

We want a structure close to:

P_i=
(
E_i,
L_i,
\sigma_i,
C_i,
E_{i+1}
)

where:

· E_i: previous expression
· L_i: law
· \sigma_i: substitution
· C_i: conditions
· E_{i+1}: result

This makes the proof independently re-verifiable.

---

Phase 7 — Build Canonical Representation

This is a delicate stage.
We need to decide when two expressions are structurally equal.
For example:

a+b

and:

b+a

are not necessarily the same tree.
But they can be considered equivalent:

a+b \equiv b+a

due to the commutativity law.
Therefore, we need to separate:

\text{Structural Equality}

and

\text{Mathematical Equivalence}

This separation will be fundamental later.

---

Phase 8 — Test the Boundaries

After success with simple algebra, we do not add dozens of features.
We try to break the system.

We test:

· Can it apply a wrong law?
    It must:
  \boxed{False}
· Can it change the substitution?
    It must be detected.
· Can it modify an old step in the proof?
    Verification must fail.
· Can it execute a circular rewrite?
    It must be prevented by cycle detection or execution limits.

These tests are more important than adding new features.

---

Phase 9 — Add a Second Mathematical Domain

After success with Algebra, we choose a structurally different domain.
I recommend:

\boxed{\text{Linear Algebra}}

because it will test UMK's ability to handle more complex objects:

Vector,\quad Matrix,\quad LinearMap

We will see whether the kernel is truly generic or whether its design was only suitable for algebraic expressions.

---

Phase 10 — Test the "Universal Kernel"

The real test will be:

```
Algebra
      \
Number Theory ----\
                   \
Linear Algebra ----> UMK Kernel
                   /
Geometry ----------/
```

If different domains can use the same:

Expr
+
Law
+
Rewrite
+
Proof
+
Verify

then that is a very strong architectural proof of the correctness of the idea.

---

Phase 11 — Only Then Start Thinking About Mathematical Intelligence

Here your original vision becomes truly interesting.
Later we can place a layer:

\boxed{\text{Discovery / Reasoning}}

on top of:

\boxed{\text{Verified Mathematics}}

where the role of artificial intelligence is:

Suggesting laws and steps.

and not:

Being the source of truth.

That is:

AI \rightarrow Candidate\ Proof

then:

Kernel \rightarrow Verification

This separation is very important.

---

Concise Implementation Plan

I suggest the following order of work literally:

1. Freeze Kernel API
   ↓
2. Define Kernel/Math boundary
   ↓
3. Create math/algebra
   ↓
4. Implement Algebra objects
   ↓
5. Implement Algebra laws
   ↓
6. Execute real derivations
   ↓
7. Generate ProofObjects
   ↓
8. Independently verify proofs
   ↓
9. Attack the verifier with invalid proofs
   ↓
10. Fix architectural weaknesses
    ↓
11. Add Linear Algebra
    ↓
12. Test cross-domain universality
    ↓
13. Only then build AI/Discovery layer

The Most Important Decision

Do not enlarge the kernel now.
Instead, make the kernel smaller and stricter, and pressure it from outside with mathematics.
If we can put algebra outside it, then linear algebra outside it, then later number theory outside it, and all of them use the same mechanism:

\boxed{
\text{Expression}
\rightarrow
\text{Law}
\rightarrow
\text{Rewrite}
\rightarrow
\text{Proof}
\rightarrow
\text{Verification}
}

then we will have practical evidence much stronger than any theoretical description that UMK is "Universal".

The next step I specifically advise implementing now is Phase 1 then Phase 2: design the Math Library ↔ Kernel interface and build math/algebra as the first external library. After that, test it on 5–10 non-trivial algebraic identities before touching the kernel again.
